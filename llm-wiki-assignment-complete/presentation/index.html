01 · WHY TOOLS?

為什麼 LLM 需要工具？

模型本身

擅長理解與生成文字，但可能缺少最新資料，也可能在精確計算或外部操作上出錯。

外部工具

搜尋、計算、資料庫與 API 能提供資訊或執行動作；模型仍要選對工具並理解回傳結果。

Agent 不只是回答問題，而是能在環境中採取行動、讀取結果並持續完成目標。
02 · REACT

ReAct：思考與行動交替

Thought→Action→Observation↺
  • Thought：整理目標、狀態與下一步。
  • Action：呼叫搜尋或環境操作。
  • Observation：接收工具回應，更新下一輪判斷。
關鍵是 Observation 能改變後續計畫，而不是模型只靠內部知識一次猜完。
03 · TOOLFORMER

Toolformer：模型怎麼學會何時呼叫？

產生候選呼叫→執行工具→比較 loss→保留有用呼叫

Toolformer 先產生候選 API 呼叫並實際執行，再比較工具結果是否改善後續文字的預測。保留有幫助的呼叫，形成資料增強語料來訓練模型。

它的主要貢獻是工具使用行為的自監督訓練，而非一套完整 Agent 執行平台。
04 · GORILLA

Gorilla：大量 API 怎麼選對？

Retriever

從大量 API 文件檢索與任務相關的介面、參數與規格。

模型生成

依據檢索到的文件，產生對應 API 呼叫，降低幻覺函式與錯誤參數。

Gorilla 將 API 使用資料、檢索與結構化呼叫評估結合。文件能提供當下依據，但不保證呼叫一定安全或達成任務。

05 · TOOLLLM

ToolLLM：多工具、多步驟任務

  • ToolBench 收集大量真實 REST API，並建立指令與工具呼叫路徑資料。
  • API Retriever 協助從大量工具中縮小候選範圍。
  • ToolLLaMA 進行多輪工具使用。
  • DFSDT 以搜尋與回溯探索替代決策路徑。
  • ToolEval 評估工具使用路徑。
若一條工具路徑走不通，回溯並嘗試其他分支，比只沿單一路徑硬走更有彈性。
06 · AGENTBENCH

AgentBench：怎麼評估 Agent？

AgentBench 以八種互動環境測試模型，包括作業系統、資料庫、知識圖譜、卡牌遊戲、側向思考謎題、家務環境、網路購物與網頁瀏覽。

模型可能擅長網頁問答，卻不擅長 SQL；也可能會產生指令，卻無法在多輪互動中追蹤狀態。

Benchmark 分數反映特定環境與設定，不等於真實世界的全面可靠性。

08 · TAKEAWAY

可靠的 Agent，需要整條鏈都做好

理解目標→選擇工具→執行與觀察→修正計畫→評估結果

五篇研究顯示，工具使用不是單一能力，而是由決策、工具知識、API 選擇、規劃、互動回饋與評估共同構成。
